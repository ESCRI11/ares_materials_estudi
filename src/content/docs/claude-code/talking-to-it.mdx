Most people treat it like a search box: type a request, take what comes back, retype the
request when it is wrong. That works, badly. It is a conversation, and the difference
between a frustrating session and a useful one is usually four or five habits that cost
nothing to learn.

## Ask it to ask you

The single most useful sentence you can add to a request is an instruction to interrogate
you first. A vague brief produces a confident answer to a question you did not ask; making
it check turns that into a two-minute exchange.

```
I want to add a form to my portfolio site so people can contact me.
Before you write anything, ask me whatever is unclear.
```

A reply looks roughly like this:

```
A few things before I start:

1. Where should submissions go — an email service, a form service
   like Formspree, or your own backend?
2. Do you want validation in the browser before it submits?
3. Should this match the styling of your existing pages, or do you
   want it to stand on its own?
```

You answer three questions and get the thing you meant. Without that sentence, you get a
form that posts to a backend you do not have.

This matters more the less experienced you are, not less — a vague brief is not a beginner
failing, it is what happens when you do not yet know which decisions exist.

## Ask for options, not a decision

When you do not know what you want, say so and ask it to lay the ground out rather than
pick for you.

```
I need to store the drawings people make in my sketch tool so they
survive a page refresh. Give me three approaches with the trade-offs,
then stop — don't implement anything yet.
```

The "then stop" is doing real work in that sentence. Without it you tend to get an
explanation *and* an implementation of whichever one it preferred, which is exactly the
outcome you were trying to avoid by asking.

You can push the same technique further when the choice is aesthetic rather than technical:

```
Propose four different visual directions for this page — for each, give
me the background colour, the accent, and the typeface, with one line on
why. Then wait for me to choose.
```

## Plan mode is this, built in

The permissions lesson mentioned plan mode. This is what it is for: `Shift+Tab` until you
reach it, and it explores your project and proposes an approach **without touching a
single file**. You read the plan, argue with it, and only then let it work.

For anything you are unsure about, plan mode first is a better default than asking and
hoping.

## Interrupt it

You do not have to wait for it to finish being wrong. Press `Esc` and it stops where it
is; then say what you actually wanted:

```
[Esc]

Stop — I don't want a separate CSS file, keep the styles in the page
like the rest of my project does.
```

It picks up from there with the correction, rather than starting over. Pressing `Esc`
twice on an empty prompt is a bigger move: it opens the rewind menu, where you can send
the conversation and its edits back to an earlier message. Use the single `Esc` unless
the whole direction was wrong.

Interrupting early is a skill worth building deliberately. The instinct is to let it
finish out of politeness, which is a strange thing to feel toward a program and costs you
several minutes each time.

## Short follow-ups work

Within a session it remembers what you have both been doing, so follow-ups can be as
short as they would be with a person:

```
Now do the same for the other two files.
```

```
That works, but explain why you used a for...of loop there instead of a
plain for loop.
```

```
Undo the last change — I preferred it before.
```

This is also the reason `/clear` exists. When you move to an unrelated task, the previous
conversation stops being context and starts being noise.

## Say what you don't want

Constraints are as useful as requests, and they are the part beginners leave out:

```
Fix the bug where the canvas doesn't clear between frames.
Change only what's needed for that — don't refactor anything else,
don't add error handling, and don't touch the styling.
```

Without that, a small fix can come back as a tidied-up file where you can no longer see
what the actual fix was.

## Make it teach while it works

Because it is a conversation, you can ask for the reasoning alongside the result — which
is the whole argument of
[the previous lesson on learning](/ares_materials_estudi/claude-code/learning-not-outsourcing/):

```
Write the function, then explain each line as if I've been programming
for two weeks. I need to be able to write this myself next time.
```

```
Before you fix it: what do you think is causing this, and what would
you check to confirm that? I want to follow the reasoning.
```

That second one is the most valuable prompt in this section. Debugging is a skill made of
hypotheses and checks, and watching someone form one is how you learn to do it.
