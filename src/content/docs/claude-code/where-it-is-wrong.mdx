Every failure in this lesson has the same shape: it looks like success. None of them announce
themselves, none of them produce an error, and all of them are written in the same confident,
well-organised prose as everything that was correct.

That is the whole difficulty. A tool that failed loudly would need no lesson.

## Plausible code that fails on an edge case

The most common one by a distance. You get code that is well structured, reads correctly, and
works on the example you tried. It breaks on the input you did not try.

An **edge case** is an input at the boundary of what you had in mind: the empty list, the value of
zero, the name with an apostrophe in it, the window resized to 320 pixels wide, the second click
before the first has finished, the microphone the user denied permission to.

```js
// looks right, and is right, until the array is empty
const average = nums.reduce((a, b) => a + b) / nums.length;
```

**Notice it by** trying the awkward input on purpose, immediately, before you move on. Empty,
zero, negative, very long, wrong type, twice in a row. Thirty seconds of hostile testing catches
most of them, and it is a habit that makes you better at writing code as well as at checking it.

## Inventing something that does not exist

It will occasionally use a function, a file, an option or a package that is not real. Not a typo —
a plausible name that fits the pattern of names in that library, produced because plausible text
is what the mechanism produces. This is
[hallucination](/ares_materials_estudi/ai-as-a-material/what-a-language-model-is/) in its coding
form, and the code equivalent of an invented citation.

You often meet it as an immediate error, which makes it the friendliest failure in this list.
Sometimes it is quieter: an option name that does not exist is ignored without complaint, so the
code runs and the setting you thought you applied does nothing.

**Notice it by** the error, when you are lucky, and by checking the documentation for anything you
have not seen before. If it names a package you have never heard of, look it up before installing
it.

## Losing your earlier instructions

Twenty exchanges in, a constraint you set at the start stops being honoured. You said no
libraries; there is now a library. You said keep it in one file; there are three.

This is the [context window](/ares_materials_estudi/claude-code/claude-md-and-commands/) filling
up. It is not the tool ignoring you and it is not fixed by repeating yourself more firmly.

**Notice it by** the reappearance of something you already ruled out. When it happens, `/clear`
and start again — with the rule in CLAUDE.md this time, since that reloads on every session and
your twenty-minute-old sentence does not.

## Vague request, vague result

Ask for "make the page look better" and you get an answer to a question nobody asked: a change
that is defensible, generic, and not what you wanted. This is the same failure as
[a bad brief](/ares_materials_estudi/ai-as-a-material/prompting/), and the same fix.

**Notice it by** reading the diff and finding a solution to a different problem. That is a
signal about your request, not about the tool. Name the file, name the behaviour you want, name
what should not change.

## Confidently explaining something wrong

The most dangerous one, because there is no error, no diff to read and nothing to run. You asked
how something works, you got a clear and well-organised explanation, and part of it is untrue.

Three subjects where this is most likely, and where being wrong costs the most:

- **Security.** How to store a key, what is safe to put in a public repository, whether input
  needs checking. Confident answers here are common and wrong answers have consequences that
  arrive months later.
- **Performance.** "This is faster" is a claim about a specific machine running specific code,
  and it is usually asserted rather than measured. Measure it or drop the claim.
- **Accessibility and standards.** Whether an element is correct for the job, what a screen reader
  announces, what the specification actually says. Plausible-sounding accessibility advice is
  everywhere in the training material, including plenty that is out of date.

**Notice it by** treating explanations in these three areas as leads rather than answers, and
checking them against the actual documentation — MDN for the web, the tool's own docs otherwise.

## Why the diff review habit catches most of this

Read the diff before approving and four of the five above become visible:

| Failure | What the diff shows |
|---|---|
| Edge case | Nothing directly — but you see the logic, so you can ask what happens when it is empty |
| Invented function | An unfamiliar name you have not seen in this project before |
| Lost instruction | The library you banned, appearing in an `import` line |
| Vague request | A change that solves a different problem from the one you had |

The fifth — a wrong explanation — has no diff, which is exactly why it is the one to be most
sceptical about. There is nothing to review, so the checking has to be deliberate.

## What never to accept without verifying

- **Anything about security.** Keys, credentials, what is safe to commit, what is safe to publish.
- **Any performance claim.** Unmeasured means unknown.
- **Any accessibility or standards claim.** Check the specification.
- **Any package or version number** you have not seen before, especially before installing it.
- **Any explanation you are going to rely on in an exam.** Confirm it against the course material
  or the documentation, because in the room it will be your answer, not its.

None of this makes it a bad tool. A knowledgeable colleague who is right most of the time, occasionally
wrong with total confidence, and never says "I am not sure" is still worth having — you adjust by
checking rather than by not asking. The adjustment is the skill.

:::tip[The two-minute check]
Before accepting anything non-trivial: run it, try one awkward input, and read the diff for a name
you do not recognise. That catches the majority of what this lesson describes, and it is short
enough that you will actually do it.
:::

That is the section. What it leaves you with is a tool you can point at your own project without
being nervous, and a clear sense of the three places it will hurt you: the diff you approved
without reading, the explanation you believed without checking, and — from
[the permissions lesson](/ares_materials_estudi/claude-code/permissions/) — the instruction that
came from a file rather than from you.
