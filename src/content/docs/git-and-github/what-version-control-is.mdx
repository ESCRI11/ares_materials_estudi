You have already invented version control. It looks like this:

```
poster_final.ai
poster_final_v2.ai
poster_final_v2_REALLY_final.ai
poster_final_v2_REALLY_final_CLIENT.ai
poster_final_v2_REALLY_final_CLIENT_use-this-one.ai
```

Every one of those files exists because you wanted to change something without losing what
you had. That instinct is right. The filing system is what fails you:

- Nothing records **what** changed between two of them, so you open both and compare by eye.
- Nothing records **why**, so in three weeks you cannot remember which one the client saw.
- If a collaborator edits one while you edit another, merging means copying elements across
  by hand and hoping.
- The names get longer, and the folder gets heavier, and you never delete any of them
  because you are not sure.

**Version control** is software that does this job properly. You keep one file name. The
program keeps the history separately, along with a note from you about each change, and can
put the folder back into any earlier state on request.

## The repository

A **repository** — everyone says *repo* — is a project folder that a version control
program is watching, together with the complete record of its history.

The record lives in a hidden folder called `.git` inside your project. You will never open
it. What matters is the consequence: a repository is self-contained. Copy the folder to a
memory stick and the entire history travels with it. Delete the `.git` folder and you are
back to an ordinary folder of files.

The history is made of **commits**. A commit is a saved snapshot of your whole project at
one moment, with a short message from you saying what changed. Not a backup of one file — a
picture of everything, at once, labelled. The next lesson makes your first one.

## Git and GitHub are not the same thing

This is the single most common confusion, and it is worth being blunt about.

**Git** is a program that runs on your computer. It was written in 2005 to manage the
source code of Linux, it is free, and it does not know or care whether you are online. Git
is what records commits.

**GitHub** is a website that stores copies of git repositories, owned by Microsoft, and free
for the kind of work you will do. On top of storage it adds the things a website can offer
and a local program cannot: a page other people can visit, a place to discuss changes, and
free hosting for simple sites.

| | git | GitHub |
|---|---|---|
| What it is | a program on your laptop | a website |
| Needs internet | no | yes |
| Where your history lives | in the `.git` folder of your project | in a copy of it on their servers |
| Who can see it | you | whoever you allow |
| Alternatives | very few in practice | GitLab, Codeberg, Bitbucket |

Git works perfectly well with no account anywhere. You could do a whole project offline on
a train and never push a thing. GitHub, on the other hand, is close to useless without git,
because what it hosts *is* a git repository.

A rough analogy: git is track changes in your document. GitHub is the shared drive you put
the document on so someone else can read it. The analogy breaks down eventually — GitHub
copies are full repositories, not a synced folder — but it gets the relationship right.

:::tip[Say it out loud once]
"Git records the history on my machine. GitHub keeps a copy online." Confusing them is the
source of about half of all beginner frustration with this topic.
:::

## Why your master cares

Creative Coding Foundations names GitHub among the tools you are expected to use, and it is
how technical work is handed in, reviewed and shown. Beyond the master, a repository is the
plainest possible evidence of how you work: what you tried, in what order, and what you
decided. Studios read that.

You are not learning this because designers should think like engineers. You are learning
it because it is where the files live.
