This lesson is done in the terminal — the window where you type commands to your computer
instead of clicking. Every command below is meant to be copied and pasted one at a time.
Nothing here touches the internet.

## Where to type all of this

On Windows, every command in this section goes into the **Ubuntu terminal** you set up in
the [WSL2 lesson](/ares_materials_estudi/your-machine/wsl2/) — the same window you have been
using since, not PowerShell. On macOS it is the terminal you already have.

You installed git there in
[installing software from the terminal](/ares_materials_estudi/your-machine/installing-software/),
so it is ready. If `git --version` answers "command not found", go back to that lesson:
`sudo apt install git` inside Ubuntu, `brew install git` on macOS.

:::note[Tutorials that tell you to download git from a website]
There are a great many of them, and on Windows they end with a separate terminal called Git
Bash. You do not need it. You have git inside Ubuntu, which is where your project files
live and where every later lesson expects you to be. A second git, on the Windows side,
with your work sitting on `C:`, is the arrangement this site spent a lesson avoiding.
:::

## Tell git who you are, once

Git stamps your name and email onto every commit, so it needs them before your first one.
This is a one-off for the whole machine, not per project:

```bash
git config --global user.name "Your Name"
git config --global user.email "you@example.com"
```

Use the email you will use for GitHub later. It is written into the history in plain text,
so pick one you are comfortable making public.

While you are here, set the name of the first branch git creates. A **branch** is a line of
commits; you get one automatically and can ignore it for now, but the conventional name for
it changed a few years ago and git nags about it if you leave it unset:

```bash
git config --global init.defaultBranch main
```

## Make a repository

Create a folder to experiment in, move into it, and turn it into a repository. Put it in the
`ind-prep` folder you made in
[moving around](/ares_materials_estudi/your-machine/moving-around/), which is in your home
directory — on Windows that is the Linux home, not anywhere under `/mnt/c`:

```bash
cd ~/ind-prep
mkdir git-practice
cd git-practice
git init
```

`git init` creates the hidden `.git` folder. That is the whole ceremony — the folder is now
a repository, and everything you do inside it can be recorded.

Put something in it. Any file will do:

```bash
echo "# Git practice" > notes.md
```

Two new pieces of shell there, both worth having. `echo` prints whatever you give it, and
`>` sends what a command prints into a file instead of onto the screen — creating that file,
or **replacing it entirely** if it already exists. So that line writes one heading into a new
`notes.md`.

## Look before you commit

```bash
git status
```

`git status` is the command you will run most. Right now it tells you that `notes.md` is
**untracked** — the file is sitting in the folder, but git has been given no instruction to
record it. Git never records anything you did not ask it to.

## The two-step save

Saving to history takes two commands, and the reason is worth understanding. A change moves
through three places, and each command moves it one step along:

```mermaid
flowchart LR
    A["Working folder"] -- "git add" --> B["Staging area"]
    B -- "git commit" --> C["History"]
```

```bash
git add notes.md
```

`git add` moves the file into the **staging area**: a tray of changes you are proposing to
save together. Nothing is in the history yet. The tray exists so that you can commit three
related changes and leave a fourth unfinished one out.

```bash
git commit -m "Add a notes file"
```

`git commit` takes whatever is in the tray and writes it into the history as one snapshot.
`-m` supplies the message inline. Leave it out and git opens a text editor *inside the
terminal*, waiting for the message — and since it has no menus and no visible way out, this
is where a lot of people's first commit stalls.

:::tip[Getting out of the editor]
Which editor opens depends on your machine, and the two you will meet leave in completely
different ways.

- **nano**, the usual one on Ubuntu, lists its shortcuts along the bottom of the screen.
  Type the message, then **Ctrl+X**, then `Y`, then Enter.
- **vim**, the usual one on macOS, starts in a mode where the keys are commands rather than
  letters. Press `i` to start typing, Esc when the message is written, then `:wq` and Enter.

In both, leaving without saving anything cancels the commit — `Ctrl+X` then `N` in nano,
`:q!` and Enter in vim. Nothing is lost; the staged changes are still staged.

If you would rather never find out which one you have, choose once:

```bash
git config --global core.editor nano
```
:::

Run `git status` again and it reports a clean working tree — no changes waiting.

### What a commit actually contains

Five things:

1. **The state of every tracked file** at that moment.
2. **A message** — your description of what changed.
3. **Author and date**, from the config you set above.
4. **A pointer to the commit before it**, which is what makes the history a chain rather
   than a pile.
5. **A hash** — a forty-character identifier like `a3f9c1e...`, calculated from the content.
   It is how git refers to that exact snapshot forever. In practice you use the first seven
   characters.

Commits are cheap. Make them small and often rather than saving up a day of work.

## Read the history

Edit `notes.md`, then do a second round so there is a history to read:

```bash
git add notes.md
git commit -m "Add a line about the staging area"
git log --oneline
```

`git log` shows your commits, newest first. Any git output too long for the window goes into
a **pager** — the one-screen-at-a-time viewer you met as `less` in
[working with files](/ares_materials_estudi/your-machine/working-with-files/). It looks like
the terminal has frozen, and it has not: **press `q` to get out**.

`--oneline` gives one commit per line rather than a paragraph each, which is what you want
most days. It does not switch the pager off — it takes far more commits to fill a screen
that way, so early on you will not see one.

To add every changed file at once instead of naming them:

```bash
git add .
```

The `.` means "this folder and everything in it". Convenient, and worth a glance at
`git status` first so you know what you are sweeping up.

## Writing a commit message worth reading

The message is the only part of a commit a human reads. In six months it is the only thing
telling you why the layout changed.

- Write it as an instruction: *Add contact page*, *Fix overlapping labels*, not
  *added stuff* or *changes*.
- Keep the first line under about fifty characters. It is a title, not a paragraph.
- Say **what and why**, never how. The how is visible in the change itself.
- If the message needs the word "and", it is probably two commits.

Compare:

```
No  — update
No  — asdf
No  — fixed the thing that was broken yesterday
Yes — Increase card padding for readability on mobile
Yes — Remove unused typeface files
```

## Undoing things

Three mistakes cover nearly everything you will do wrong this week, and each has a one-line
answer. They are also the reason committing often is worth the habit: anything already
committed is recoverable, and these commands are how you reach back for it.

**You edited a file and want it back the way it was.**

```bash
git restore notes.md
```

That throws away your changes to `notes.md` and returns it to how it looked in the last
commit. `git restore .` does it for every file in the folder at once.

:::caution[This one is not recoverable]
`git restore` discards work that was never committed, and uncommitted work has no copy
anywhere. Git can only give you back what it was told to record. Read the filename before
you press Enter.
:::

**You staged a file you did not mean to.**

```bash
git restore --staged notes.md
```

That takes the file back out of the tray. Your edit is untouched — you are only telling git
not to include it in the next commit. `git status` shows it as changed but no longer staged.

**You committed with a bad message, or forgot a file.**

```bash
git commit --amend -m "The message you meant to write"
```

`--amend` replaces the last commit rather than adding another. Stage a forgotten file first
with `git add` and it goes into that same commit. Do this only for a commit that is still on
your machine: once a commit has been sent to GitHub, other people may have it, and replacing
it underneath them causes exactly the confusion you were trying to avoid.
